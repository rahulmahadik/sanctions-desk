# Evaluation

How the desk is measured, what each variant is, and how to run it. The results themselves are in [eval/REPORT.md](../eval/REPORT.md), built from the files in `eval/results/`.

## The headline measure

One measure is used everywhere (the report, the README and the interface), computed by `packages/agents/src/headline.ts` from the cases of an exam run:

| Part                                 | Meaning                                                                                                                                                                                        | Measured or assumed                                                                                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Closed with evidence                 | Alerts the desk recommended closing as false positives, with the facts cited. A person still confirms each one.                                                                                | Measured                                                                                                                                                                    |
| Escalated                            | Every other recommendation (escalate, block, need more information).                                                                                                                           | Measured                                                                                                                                                                    |
| False-close rate                     | Of the cases where closing is wrong (the true matches and every other risk case), the share the desk recommended closing. Target: 0. Reported for all risk cases and for the true-match group. | Measured                                                                                                                                                                    |
| Analyst minutes saved per 100 alerts | 100 × (share of alerts closed _rightly_) × (minutes per alert − minutes to confirm a close)                                                                                                    | **Assumption**: `report.minutesPerAlert` (15) and `report.minutesToConfirmClose` (2) in `config/default.json`. Escalated alerts get no credit. A wrong close earns nothing. |

## The exam

70 cases built from real public list entries and synthetic customers, payments and owners, in twelve groups: false positives, true matches, transliteration, missing data, hidden ownership at and above 50 percent, ownership below 50 percent, earlier clearances that still hold, earlier clearances that no longer hold, injection, tipping-off drafts, payment routes through watched jurisdictions, and cases where plain name matching is likely to fail (reversed names, aliases, partial birth dates, a birth-date match with another nationality, a watched place named only in the payment reference). Each case has one right answer, acceptable alternatives and answers that must never be given. Edge cases are listed in [EDGE_CASES.md](EDGE_CASES.md).

## Variants

| Variant        | What it is                                                                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `routed`       | The full system: Nemotron models through Nightshift (Nightshift's router decides which model serves each call), safety guard, decision, critic, challenger, memory, policy guard                                                |
| `single`       | One recommendation: no critic, no challenger, no memory                                                                                                                                                                         |
| `no_memory`    | The full system with memory off, run on the earlier-cleared cases                                                                                                                                                               |
| `local`        | The full system asking for the fast mode only, with no reasoning budget. Nightshift still decides which model serves it, so this is not a guarantee of local answers                                                            |
| `rules`        | The **deterministic pipeline**: our own matching, ownership and policy code with a labelled rules stand-in in place of a language model. It reads the same evidence as the full system, so it shows what the code alone settles |
| `fuzzy`        | The **name-match rules baseline**, which stands for typical screening: a name score at or above 0.90 escalates, below closes, with no ownership, data-quality or evidence reasoning                                             |
| `escalate_all` | Every alert goes to a person                                                                                                                                                                                                    |

## Running

```bash
npm run exam -- --variant routed          # one variant, once; writes eval/results/<time>-<variant>.json
npm run bench -- --variant routed --runs 3 --batch 20     # unattended repeated or random-batch runs
npm run exam:report                       # rebuild eval/REPORT.md and the headline in the README
npm run json:rate                         # how often a model answer could not be used as JSON, from the traces
```

`npm run bench` runs the exam, or random batches of alert cases, any number of times without attention. It writes the usual result file of every run and a summary (`eval/results/bench-*.md` and `.json`): mean and range of accuracy, false-close rate and median time, the model calls by the model that served them, and the model cost, with tokens served by the local model counted and priced at zero. Options: `--runs N`, `--batch K`, `--seed N` (repeat the same random batches), `--name`, `--case-timeout-min`, `--dry-run`, and several variants separated by commas.

Runs that were limited to some cases (a tag, `--kinds`, `--groups` or `--limit`) are kept apart: the report uses only complete runs.

## Reading the numbers

- Each variant in the report is **one run**. Model answers vary between runs.
- The runtime may answer a repeated prompt from its cache; evaluation runs use their own app id so that live use does not warm it, but a second run of the same variant can still be faster and cheaper than the first.
- A case where no model gave a usable decision is escalated with the reason "model decision unavailable". It is counted in the totals and reported separately (provider failure or unusable answer), together with the accuracy without those cases.

| 2              | **Documentary evidence standard.** A customer note or payment reference counts as documentary evidence only when it carries a check reference, a document number and a date (and, for a payment, a named counterparty). Anything less is a claim and leads to NEED_MORE_INFO. A qualifying note that states a date of birth supplies it when the customer has none on record.             | After the main exam runs and before the held-out run | None. ## The exam, every variant and the saved results

The exam has <!--fact:exam_cases-->70<!--/fact--> cases built from real public list entries and synthetic customers, payments and owners, in <!--fact:exam_groups-->12<!--/fact--> groups (false positives, true matches, transliteration, missing data, hidden ownership at and above 50 percent, ownership below 50 percent, earlier clearances that still hold, earlier clearances that no longer hold, injection, tipping-off drafts, payment routes through watched jurisdictions, and a rules gap). Each case has one right answer, acceptable alternatives, and answers that must never be given. The most important number is the **false-close rate**: how often a case that carries real risk is recommended for closing. The target is zero.

Every variant is one command, and each is a separate saved result:

```bash
npm run exam -- --variant routed          # the full system, live
npm run exam -- --variant single          # one recommendation: no critic, no challenger, no memory
npm run exam -- --variant no_memory       # the full system with memory off (the previously cleared cases only)
npm run exam -- --variant local           # reasoning off everywhere, the local model only
npm run exam -- --variant lightning       # decision, critic and challenger sent to the local model
npm run exam -- --variant rules           # our deterministic pipeline, no language model
npm run exam -- --variant fuzzy           # baseline: a name-score threshold
npm run exam -- --variant escalate_all    # baseline: every alert goes to a person
npm run exam -- --variant routed --exam heldout   # the same, on the held-out set the rules were not written for
npm run bench -- --variant routed --runs 3        # repeat runs or random batches unattended
npm run exam:report                       # builds eval/REPORT.md from the saved results
```

Results from real runs are in `eval/results/` and summarised in [eval/REPORT.md](../eval/REPORT.md). The exported evidence of the final runs (events, signed receipts and results, with local paths and addresses removed) is committed in `eval/runs/` and can be checked from a fresh clone, as shown in [Check which model served each call](MODELS.md#check-which-model-served-each-call). Nothing in them is edited by hand.

## One-command proof

**Check the claims without Docker.** With Node 24, `npm ci && npm run prove` runs seven checks in a few seconds once installed and prints one PASS or FAIL line each, then a summary; it exits with 1 if any check fails. It needs no credentials and no services, forces sample mode and never reads `.env`:

| Check                  | What it does                                                                                                                                                                                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sample-mode review     | Starts the API in the same process, runs `POST /run` for ALR-0004 and checks the sealed record on disk: its SHA-256 hash verifies and the answer carries the sample notice                                                                                              |
| Engine conformance     | Runs the vendored conformance suites of H-MEM, the World Model and the Markovian engine (`npm run test:engines`) and reports each score                                                                                                                                 |
| Critic mutation test   | Changes one cited fact at a time to a false value and runs only the critic against the same evidence; every change must be caught and unchanged decisions approved. Also checks the evidence standard and the grounding of screener signals (`npm run critic:mutation`) |
| Signed evidence        | Verifies every receipt signature in `eval/runs` and that every model call in the traces has its receipt naming the same model (`npm run evidence:verify`)                                                                                                               |
| Roles and four-eyes    | Runs the API's access tests (every role against every route that changes something) and the human-decision tests, and reports the pass counts                                                                                                                           |
| Preregistration        | Recomputes the held-out case-file hashes pinned in the tests, checks that the final freeze commit of the second held-out set is in the history, and that the third and fourth sets\' files equal the ones in their freeze commits                                       |
| No secrets in the tree | Scans the tracked text files for credential-bearing URLs, private keys and tokens, and reports counts only                                                                                                                                                              |

`npm run prove -- --verbose` also prints what each check printed. `npm run prove -- --fresh` clones the current commit into a temporary folder, runs `npm ci --no-audit --no-fund` there and runs the same checks inside it; it needs network access for npm and takes a few minutes. `npm run prove -- --write` writes the list to `eval/PROVE.md` and to the block at the top of the README.

## Benchmark command

One command runs the exam unattended, once or many times, or on random batches of alert cases, and writes a results file and a summary:

```bash
npm run bench -- --variant routed                        # the full exam once
npm run bench -- --variant routed --runs 3               # the full exam three times
npm run bench -- --variant routed --batch 20 --runs 5   # five random batches of 20 alert cases
npm run bench -- --variant routed,single --runs 2        # several variants, one after another
```

`--seed N` repeats the random batches exactly, `--name` labels the output, and `--dry-run` prints what would run. Each run is a separate `npm run exam`, so one failing run does not stop the rest. The summary (`eval/results/bench-*.md` and `.json`) gives the mean and range of accuracy, false-close rate and median time over the runs, the model calls by the model that served them, and the model cost: cloud tokens are priced under the unit costs in `config/default.json`, and tokens served by the local model are counted and cost nothing. `npm run json:rate` reports how often a model answer could not be used as JSON, from the traces of the runs.
