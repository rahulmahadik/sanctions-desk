# Known issues

Problems that are still true, with what the desk does about each. Facts only; versions are the ones used during development (Zetaris 2.4.x local, Nightshift runtime 1.2.1, Ollama with `nemotron-3.5-lightning:30b`). Problems met while building and since fixed are in [RESOLVED_ISSUES.md](RESOLVED_ISSUES.md).

Each row starts with its status: **Handled** (the problem is still there, and the desk works around it), **Changed** (a policy change whose cost is still there), or **Open** (still true: a limit of the platform, or not done). Open issues are listed first.

## Open issues

- **The safety guard misses some injected text.** Through full reviews with the guard asked twice, 27 of 28 reviews of injected text were caught; the miss (an instruction hidden in an HTML comment in an ordinary note) closed in an alert whose own data closes. With the guard asked once, 2 of 70 unflagged texts closed the same way. An unflagged text has not turned an escalating case into a close (0 of 4 runs). See [EVALUATION.md](EVALUATION.md#safety-guard-against-injected-text).
- **The reviewer-addressing check raises false alarms on real data.** In a live test it flagged ALR-0073, whose free text is an ordinary payment reference ("Machine parts, onward delivery to Tehran") and an OFAC remark that links to the list's directives page; the two main guard calls said clean. It flagged that alert in 4 of 4 live runs, giving as its reason that the text names sanctioned parties or a directive and an onward delivery. Two fixes were tried live and neither stopped it: removing the OFAC link boilerplate from the text it reads, and giving it only the free-text fields with a sentence saying that listed names and remarks are the subject of the review. Both were reverted. The flag is fail-safe (it can stop a close, never cause one): over the 51 recorded reviews made with this check (47 adversarial test runs and 4 runs of ALR-0073) it flagged 27, and stopped 0 proposed closes, because none of those reviews proposed a close. The flag is also shown to the decision step, so it may have steered some of those escalations. A flag from this check alone could become a note for the reviewer instead of a stop, but on the fresh test set the safety guard caught 26 of 28 reviews of injected text and 9 of those were caught only by this check, so it is left as it is. Its reason is kept in the trace, shortened and with any quoted text removed.
- **`matching.strongIdentifierFields` and `minStrongIdentifierMatches` in the policy file are not used.** The schema checks them (four fields, at least 2), but no step reads them. The code counts strong identifier matches as date of birth exact, nationality matching a listed country, and any document number matching (0 to 3), reports that count in the comparison, and decides the match strength with fixed combinations in `assess` ([compare.ts](../packages/data/src/matching/compare.ts)): for example a document match with a name score of at least 0.7, or a high name score with an exact date of birth and a matching nationality. Changing those two settings changes nothing.
- **Payment alerts use a false-positive test the approved wording does not describe.** The approved `false_positive` definition speaks of the customer's date of birth and nationality, which a payment counterparty does not have. For a payment, the code marks the comparison as a false positive when the counterparty's country is not one linked to the listed party and no document number matches (`compare.ts`, the payment branch). No definition row covers this case.
- **The screener over-flags harmless text** (5 of 15, then 7 of 16 reviews), so many correct clears go to a person. See below and [EVALUATION.md](EVALUATION.md#safety-guard-against-injected-text).
- **Raw text can reach the cloud before the desk refuses the answer.** Nightshift's router decides where a call runs. A cloud-served guard or screener answer is not accepted and the case is held, but the text has already been sent. 7 guard calls in runs made before cloud answers were refused were cloud-served; in four early runs, made before the screener existed (the headline 70-case run, single, no_memory and held-out v1), payment references and list remarks were in the cloud decision prompt ([PRIVACY.md](PRIVACY.md#earlier-runs)).
- **Zetaris keeps the literal document number** that the note check sends, in its own statement history; the desk's record keeps only its hash ([PRIVACY.md](PRIVACY.md)).
- **The committed run files contain synthetic free text** in old trace lines and in receipt previews, which cannot be edited without breaking their signatures ([PRIVACY.md](PRIVACY.md)).
- **A saved policy folder wins over the policy file.** Once `logs/policy/` exists, a restart reads the saved versions, not `config/policy.default.json`; to start from a changed file (for example policy version 9), move that folder aside or publish the change through the policy routes ([GOVERNANCE.md](GOVERNANCE.md)).
- **An old users file stops a live start.** With sign-in on, a users file from a version that issued tokens in another form must have each such token rotated (`npm run users:rotate`) before the server starts.
- **Two copies of the local model, and a cold backup.** The Ollama backup keeps its own 19.5 GB copy of the local model (Nightshift holds another, about 24.6 GB resident) and loads it on demand, so a backup answer starts cold. Proposed, not done: keep one local copy loaded (point the backup at the resident lane, or unload Ollama's copy), record the provider error type in the trace, and avoid other heavy work during runs. The retry fix that went with it is in [RESOLVED_ISSUES.md](RESOLVED_ISSUES.md#zetaris).
- **Biome 2.6.2 does not settle on the long route table in `docs/API.md`**, so that file is formatted by `npm run openapi:export` and left out of Biome's checks.

## Not built / not verified

- **The local screener over-flags.** On held-out v2 its blocking "relationship to listed party" signals pointed at text with no relationship word and no name (often the first 30 characters of a note), and no clear was made (0 of 5). A span-grounding check and a list of citable sources were added after that run and tested once, blind, on held-out v3 (an unseen set frozen before the fix): it made things worse on risk, **2 of 6 risk cases were wrongly closed** (a son of a listed person, a nominee). The screener flagged both relationships at 0.9 but grounding marked them not grounded; the decision first escalated, citing them; the critic rejected those citations as not citable and the decision then closed; and under policy 7 the guard let a close stand on signals that were not grounded; no clear was made (0 of 6), four of them because the note's document was not on the customer record. Reported as run; the v2 numbers are reported as they were. The grounding window was not widened and v3 was not re-run; instead policy version 8 fails closed: a signal marked not grounded is still shown and still blocks a close. On held-out v4 (the last round, frozen before that change) no risk case was closed (0 of 6), and no clear was made either (0 of 6): every clear met the documentary standard with its document on the customer record, but each carried a relationship signal at 0.9 that the screener could not ground, and that blocks under policy 8. **The desk does not clear alerts beyond what the rules clear**; its measured value is the risk it does not close.
- **Critic deadlocks.** When the decision cited a source the critic cannot check by design (a free-text column, an identifier number, a computed block), both repeated themselves for three rounds and the guard escalated. The decision step gets the list of citable sources and such citations are set aside from the second round; on held-out v3 one deadlock still happened (HO3-012), and on v4 one (HO4-012). The critic still tells the decision step that screener signals cannot be cited, which is how both v3 wrong closes came about; under policy 8 the guard blocks such a close, but the critic rule itself is unchanged (feature freeze).
- **Thermal limits.** Long runs on one laptop drive the model runtime into a serious thermal state; the runner cools down between cases and pauses when it lasts. Provider failures are counted per run and shown by thermal posture for the 70 cases, v1 and v2. The routed v4 run ran without the gate (see Limits).
- **Nemotron 3 Super 120B.** The runtime lists it, but its cloud endpoint was retired during development (it answered "Function not found"), so the cloud lanes use Nemotron 3 Ultra. From development notes; not re-measured.
- **Single runs.** Every result in the recorded evaluation is one run. A small study, not part of it, ran held-out v4 three times each with the full system, Nemotron alone without the free text, and Nemotron alone with it ([NEMOTRON.md](NEMOTRON.md#what-the-agents-add-over-nemotron-alone)). Held-out v4 was the last held-out round; nothing was changed after it.
- **Not measured:** a run without Zetaris other than the unreachable-endpoint test, the policy guard switched off, the challenger alone, and a pinned-model run. A "Nemotron alone" baseline and the Lightning-versus-Ultra comparison were run only as small labelled studies ([NEMOTRON.md](NEMOTRON.md)).

## Considered, not done

- **Exact model pinning not done:** the Nightshift release with exact model selection was not available before submission, so the desk stays on Nightshift 1.2.1, where the router chooses the model within a lane; the receipts record the model that answered every call.
- **Nemotron embedding for finding earlier decisions by meaning.** Nightshift 1.2.1 lists `nvidia/nemotron-3-embed-1b` and a `meterless/embed` mode, but no route returns an embedding: `/v1/embeddings` answers 404, and a chat call in the embed mode answers 400 `class_carrier_unsupported` ("no route on this build returns embed"). No embedding call can be made with a receipt, so memory recall stays on exact pointers. No rerank model is listed (`/v1/rerank` answers 404).
- **An NVIDIA guard or jailbreak-detection model as a second opinion in the safety guard.** Nightshift 1.2.1 does not serve one: a call naming `nvidia/llama-3.1-nemoguard-8b-content-safety` or `nvidia/nemoguard-jailbreak-detect` is answered, but its receipt names Nemotron 3 Ultra, the general model. Ollama on this machine has no such model, and adding a lane is a Nightshift provider setting this project does not change. The safety guard stays on Nemotron 3.5 Lightning plus the fixed patterns.

## Exported run files

- **The `results.json` files of the 28 exported runs differ from their manifest hash by one documented field.** Each `run-meta.json` keeps the SHA-256 of its files as exported. When the history was rewritten, the `commit` field in every `results.json` was re-pointed to its rewritten id, following the commit map; nothing else changed. `eval/runs/HASH-CHANGES.json` lists each file's original hash, its hash after the remap and the old and new value, and `npm run evidence:hash-changes` puts each old value back and confirms the original hash. `npm run evidence:verify` and `npm run prove` report these files as "verified, commit field remapped (documented)" and fail on any other difference. The trace and receipt files match their manifest hashes unchanged.

## Limits

- **Limitation:** By default the cloud decision model receives structured personal fields from the case (name, date of birth, nationality); the desk does not put free text in a cloud prompt itself, but 7 safety-guard calls in runs made before cloud answers were refused were routed to Ultra in the cloud, and Nightshift's answer memory (on during the recorded runs, off in the desk's configuration) could add earlier answers to cloud calls ([PRIVACY.md](PRIVACY.md)). In four early runs, made before the screener existed (the headline 70-case run, single, no_memory and held-out v1), the cloud decision prompt held payment references and list remarks; customer notes were never in it. In every run with the screener, a check keeps all free text out of cloud prompts. The optional privacy mode sends tokens instead, and has been tested only on a small live sample.
- The customers, accounts, owners and payments are **synthetic**; only the listed parties are real public entries. The exam measures behaviour on planted situations, not performance on a bank's real alert volume.
- The approved definitions are written in this repository for the exam, and the exam's labels follow the same definitions. A high score shows consistency with them, not that they are the right ones for a given bank.
- Each variant in the report is one run. Model answers vary between runs and the runtime may answer a repeated prompt from its cache.
- Speed: the first-system run of the 70-case exam took a median of 130 seconds per alert (the headline measure), because it uses a large cloud model, a critic and sometimes a challenger; the changed system took a median of 62 seconds a case on the same cases and 45 seconds on held-out v4. One run each, on one laptop.
- Cost figures use illustrative unit costs. Analyst time saved was not measured; the report's minutes-saved figure is an estimate on stated assumptions and is not claimed here.
- Sanctions law and list programmes change; the jurisdiction list is an example.
- Embeddings are not used: this Nightshift build serves no embedding route.
- Zetaris model access is set in its interface and is emptied by a rebuild; the HIDE policy on identifier numbers is configured but not enforced by this local edition, so the application enforces it in the SQL guard and the masking, and tests prove it. See `docs/ZETARIS.md`.
- Model answers vary between runs, and cloud routing is decided by the runtime.
- **The local screener over-flags relationships**, so on the held-out sets the correct clears go to a person: the fail-closed rule (policy version 8) makes every signal at or above its threshold block a close, grounded or not. On held-out v4 that cost all six clears; no risk case was closed.
- **The routed held-out v4 run ran without the thermal gate** (an operator slip, recorded in the run log); the single, rules and escalate-all runs of v4 used it. It was not re-run, so the set stays run once.

## Future work

- **Future work:** For deployments that require it, make privacy mode the default once a full evaluation run confirms it, or keep the decision step local.
- **A stronger local screener model**, so fewer relationship signals are raised on text that holds no relationship, and correct clears are not held back by the fail-closed rule.
- **Keep all raw text on the machine.** The local safety guard and screener read notes and payment references, and the cloud steps get structured signals. An answer from a cloud route is not accepted and the case cannot close, but by then the text has left the machine. The next step is a route that can only run locally.
- A pinned-model run (exact model per step) once Nightshift 1.2.3 is installed, and repeated held-out runs to show the spread between runs.
