# Security

What the desk protects, how, what was tested, and what is not covered. Scans were run against this repository and a local API only; nothing outside this machine was tested.

## What is protected, and how

| Risk                                                 | Control                                                                                                                                                                                                                    | Where                                                |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Someone acts without being who they say              | Bearer tokens per person, stored only as SHA-256 hashes in a users file outside the repository; compared in constant time; every route except `/health` needs one once sign-in is on (the default live)                    | `packages/shared/src/auth.ts`, `apps/api/src/app.ts` |
| A person does more than their role allows            | Roles `analyst`, `approver`, `policy_admin`, `viewer` with a fixed permission table; checked before any handler runs, against the route that matched and not against the text of the address (the router decodes `%32` to `2`, so the text can differ from the route) | `PERMISSIONS`, `permissionFor`                       |
| An approver approves their own decision              | The second approval of a block must come from a different person and an approver; a policy publish from a different policy admin than the author; the author and approver come from the token, never from the request body | `human-decision.ts`, `routes/policy.ts`              |
| A caller claims a role or a user in a header or body | Ignored: only the token decides; an unknown field is rejected; a body that names someone else is refused                                                                                                                   | `people.test.ts`                                     |
| Demo users reach a live system                       | They exist only in sample mode; with sign-in on or outside sample mode the demo header is ignored                                                                                                                          | `createAuthenticator`, `resolveAuthMode`             |
| A token leaks                                        | Never logged, never in a URL (the live stream is read with `fetch`, not `EventSource`), not in error bodies, not in the audit file; the redactor scrubs secrets from logs and traces                                       | `people.test.ts`, `packages/shared/src/redact.ts`    |
| A model or a user writes to a source system          | The data path is read-only by schema and by an SQL guard that allows one `SELECT` on the model's tables and, per agent, only that agent's tables and columns                                                               | `packages/zetaris/src/*`                             |
| Text in the data steers the desk                     | Treated as data; flagged by a guard model and fixed patterns; can never close a case                                                                                                                                       | `safety.ts`, `policy-guard.ts`                       |
| The desk reveals screening to a customer             | Drafts are checked against the written tipping-off policy before they are prepared; nothing is ever sent                                                                                                                   | `actions.ts`, `safety.ts`                            |
| A record or an action is altered afterwards          | Decision records are hash-sealed and chained; action records are hash-sealed or Ed25519-signed (key outside the repository) and verified on read                                                                           | `records.ts`, `actions.ts`                           |
| A path in a URL reaches a file                       | Case, run and receipt ids are matched against a strict pattern before any file is read: letters, digits, dot, underscore and dash, a letter or digit first, never `..`, so `.` and `..` cannot name a folder                | `apps/api/src/ids.ts`, `routes/*.ts`                 |
| An error repeats what the caller sent                | Errors from the router (an address that is too long or badly encoded) have the same fixed shape and wording as every other error; they do not repeat the address                                                           | `frameworkErrors` in `app.ts`                        |
| Another website frames the desk or reads its replies | The API answers only the configured web origins, never with credentials; the interface sends frame, type-guessing, referrer and plug-in headers; the compose file publishes both ports on `127.0.0.1` only and drops all container capabilities | `app.ts`, `apps/web/next.config.ts`, `docker-compose.yml` |
| A vulnerable tool ships in an image                  | The images keep Node but not the package manager, which is used only to install; CI pins its actions to a commit and fails on a high or critical dependency finding                                                         | `Dockerfile`, `.github/workflows/ci.yml`             |
| Automatic closing goes wrong                         | Only a certain close, only under listed conditions, a daily cap, a random quality-assurance sample, a kill switch; escalations, requests for information and blocks always go to a person                                  | `autonomy.ts`, `policy.ts`                           |

## Not covered

- **Transport and sessions.** The API speaks plain HTTP on the local machine. A deployment needs TLS in front of it, a way to rotate and revoke tokens (today: edit the users file), and a rate limit. None of these is built.
- **Token strength is the operator's choice.** `npm run users:add` makes a 192-bit random token; nothing stops an operator writing weaker ones into the file by hand.
- **The model service.** What leaves the machine to the cloud model is whatever the prompts hold (masked identifiers are never sent). With real customer data that needs an explicit decision.
- **The Zetaris column mask.** The Zetaris HIDE policy for `customer_identifier.id_number` is configured for the evidence role, but this local edition does not enforce it. The application enforces it instead: the SQL guard stops every agent except the evidence step from naming the column, the evidence step's masking returns only the last two characters, and a customer identifier is compared with a listed one by a join inside Zetaris so the number is never read into the application. Tests prove each part (`packages/zetaris/test/guard.test.ts`, `client.test.ts`, `tools.test.ts`). ([KNOWN_ISSUES.md](KNOWN_ISSUES.md)).
- **Synthetic data only.** No real customer data was used or tested.
- **Nothing here ran against the live data service or the model service.** The latest pass used sample mode only. The SQL guard was tested as a function, not through a live query; whether the data service honours a backslash escape (finding 10), enforces its own grants against a statement the guard let through (finding 3), or limits an expensive statement was not tested.
- **Injection resistance of a real model.** The sample tests prove that text in a note, reference or remark cannot change a decision made by the rules-based stand-in, that it cannot change the person's recorded decision, and that it renders as text. They do not show that a cloud or local model resists the same text. That is measured by the exam's injection group and the adversarial set in the evaluation, not by these tests.
- **Tipping-off checks use fixed patterns plus a guard model.** The sample test above covers the pattern path only.
- **Browser-side behaviour.** The interface was checked by its component tests and its header configuration, not by a browser-driven attack (script injection through a rendered value, clickjacking in a real browser, local-storage theft). The headers are tested as configuration; a running interface was not probed.
- **The built interface image.** Not rebuilt or rescanned after the Dockerfile change.
- **Denial of service.** No rate limit, no cap on reviews in flight (finding 9); the size limit and per-call timeouts exist. A slow-request or many-connection test was not run.
- **Concurrency beyond four requests.** The race tests send four decisions and two publishes at once in one process. A second server process sharing the log folder was not tried.
- **Timing.** Token comparison is written to take the same time whichever user matches; the timing itself was not measured.
- **Supply chain beyond the lock files.** Packages are scanned for known vulnerabilities, not reviewed for malicious code, and install scripts are skipped in the images (`--ignore-scripts`) but not in a developer's own install.
- **Mutable tags for base images.** The images start from `node:26-alpine` and `postgres:16-alpine` by tag, not by digest.
