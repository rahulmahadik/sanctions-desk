A review desk for sanctions-screening alerts

Sanctions Desk

The desk gathers and checks the evidence for every sanctions-screening alert and recommends an outcome. A person with the right entitlement approves it.

Every review leaves a sealed record, signed receipts and a step-by-step replay. Nothing in it blocks an account, writes to a source system or contacts a customer.

The problem

Thousands of alerts, and the one that is real

A bank's name screening raises thousands of alerts. Most are near-matches on a common name, and analysts work each one by hand: they pull the list entry, the customer and the payment from separate systems, compare them and write up why the alert can be closed. The work is slow and repetitive, and the costly mistake is the rare one: closing the alert that is a real match.

  1. 1

    Gathers

    Reads the list entry, the customer, the payment and the ownership chain through Zetaris, one semantic layer, with a read-only role for each step that reads data.

  2. 2

    Checks

    Code gives a first finding, a critic re-reads every cited fact from the data (at most three rounds), a challenger argues against a doubtful close, and a policy guard can only add caution.

  3. 3

    Recommends

    One of four outcomes (close as a false positive, escalate, ask for more information, recommend a block), with what decided it and what would change it, for a person to approve or override.

Who uses it

Three people, three views of the same record

Every outcome is a recommendation for approval by a person with the right entitlement. Automatic closing is off by default.

Analyst

works the alert

  • a prepared case: the customer, the listed party, the payment and the data-quality results, with identifier numbers masked
  • the recommendation, what decided it, what would change it, and any risk signal marked in the free text
  • approves it or overrides it with a written reason; a block then waits for a second approval, and an override towards less caution needs an approver

Senior reviewer

the approver role, with the approval entitlement

  • everything the analyst sees, and the same decision panel
  • gives the second approval of a block: the first may come from an analyst or an approver, the second must be a different person with the approver role
  • may override towards less caution (an override to a close waits for a second, different approver), and can stop automatic closing at once

Auditor

the read-only viewer role

  • reads everything and changes nothing
  • the sealed decision record of every review, and a signed receipt for every Nightshift answer, checkable against the pinned key
  • a replay of each run event by event, and the audit log of every action, accepted or refused, under the person's id

How it is built

Zetaris for data, Nightshift for models

Built on Zetaris, the only data path (one semantic layer over the sanctions lists, a bank database and a payments service); Meterless Nightshift, the primary path for every model call to local and cloud Nemotron models, where every Nightshift answer carries a signed receipt; local backup answers are labelled (a local Ollama backup answers only if Nightshift fails, and has no receipt by design); and three Meterless engines, each in a working feature: H-MEM (memory of earlier decisions), the World Model (the ownership register the 50 percent rule is evaluated on) and Markovian (re-screening earlier decisions after a list change).

This site is documentation only. It is static and makes no call to the desk, its API or any other service until you press play on the video, which then loads from youtube-nocookie.com. To try the desk, run it in sample mode as the README describes.

Which model does each step

  • Safety guard (inbound)Nemotron 3.5 Lightning · local
  • Free-text screenerNemotron 3.5 Lightning · local
  • DecisionNemotron 3 Ultra · cloud
  • CriticNemotron 3 Ultra · cloud
  • ChallengerNemotron 3 Ultra · cloud
  • Safety guard (outbound drafts)Nemotron 3.5 Lightning · local
